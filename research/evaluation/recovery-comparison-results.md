# Recovery schedule comparison: no advantage in the development pilot

## Answer

The tested systematic heuristic did not improve detection over either control.
It detected the known defect on its second execution in all three repetitions;
random selection detected it on executions 1, 1, and 2, and the adapted regression
on execution 1 every time. Systematic and random selection reached the same coarse
observed coverage. This rejects the proposed heuristic's advantage on this pilot.
It does not establish that every systematic exploration method is ineffective.

The scientific objective remains open. These experiments identify a real, reproducible
problem, but neither that known problem nor this unsuccessful heuristic constitutes
a new contribution. We will not tune the ordering on these results and present the
same defect family as independent validation.

## Frozen comparison and results

The [protocol](recovery-comparison-protocol.md) and
[runner](../scripts/compare_recovery_schedules.py) were committed in
`b852fb53137f745fa186144c7c155ae8c7ab47ec` before
[CI run 38033588999](https://github.com/charifmahmoudi/temporal-agent-harness/actions/runs/38033588999).
There were 72 executions, one known defect family, three repetitions per method,
four trials per repetition, and two SDK releases. Random selection sampled without
replacement. The regression baseline uses the known schedule in the shared workflow;
it is not the entire upstream regression suite.

Affected SDK 1.8.0:

| Method | First detection, repetitions 0 / 1 / 2 | Repetitions detecting by budget 1 / 2 / 3 / 4 | Typed failures / trials | Coverage pairs per repetition |
|---|---|---|---:|---|
| Systematic heuristic | 2 / 2 / 2 | 0 / 3 / 3 / 3 | 6 / 12 | 2 / 2 / 2 |
| Seeded random | 1 / 1 / 2 | 2 / 3 / 3 / 3 | 9 / 12 | 2 / 2 / 2 |
| Adapted regression | 1 / 1 / 1 | 3 / 3 / 3 / 3 | 12 / 12 | 1 / 1 / 1 |

All 36 SDK 1.9.0 trials replayed successfully. None of the 72 trials was inconclusive.
A typed failure counts as another occurrence of this known defect, not a distinct bug.
Coverage is the pair `(update accepted work, activity completion before update
sequencing)`. It measures two observed situations, not complete causal coverage.
The regression's lower coverage did not impair detection of this known defect.

Cumulative measured trial time to first detection, excluding shared setup:

| Method | Repetition 0 | Repetition 1 | Repetition 2 |
|---|---:|---:|---:|
| Systematic heuristic | 0.736 s | 0.534 s | 0.685 s |
| Seeded random | 0.370 s | 0.218 s | 0.683 s |
| Adapted regression | 0.517 s | 0.518 s | 0.520 s |

These are descriptive wall times from one time-skipping test-server job, not stable
performance estimates. They accumulate only that method's trials, excluding time
spent interleaving other methods. Environment setup took 0.900 s for SDK 1.8 and
0.197 s for SDK 1.9; full arm times were 14.035 s and 13.502 s. Package installation
and CI provisioning are outside these timings. No minimization was performed.

## Evidence and verification

[Complete evidence](recovery-comparison-evidence.json) retains all 72 compressed
histories, their digests, live outcomes, typed replay exceptions, schedules, and times.
The [derived summary](recovery-comparison-summary.json) is generated by
[the evidence checker](../scripts/summarize_recovery_comparison.py):

```sh
python research/scripts/summarize_recovery_comparison.py
```

The checker validates every history digest, activity event IDs, update sequencing,
coverage classification, trial uniqueness, planned schedule, and typed-error scoring.
Deliberately corrupted digests, duplicated trials, mismatched server hashes, and
untyped defect records were each rejected. Both release arms used Python 3.12.15,
matched dependency pins, identical workflow source, and the same server executable
with SHA-256 `19defb9f7318c7cf249518b3642a735efb79876c2b6918afe312336476b796a5`.
The binary is shared and identified within this run; future runs still download the
SDK default and must compare its digest rather than assume an immutable download.

## Consequence for the research direction

Stop the claim that this boundary ordering improves discovery. Reordering the known
trigger to position one would merely encode the regression's existing knowledge.
Three seeds and one inspected defect family cannot support a broader method claim.
The activity-latency domain also omits cache eviction, pagination, and local-activity
reconstruction, so those mechanisms remain untested.

The next justified research step is a mechanism comparison across distinct recovery
defects, followed by a specific limitation of an existing method that can be tested.
A broader generator should only be built once that limitation is identified. Issues
already read remain development cases; independent evaluation needs uninspected
cases selected before method tuning. More executions of #673 alone will not fill
that gap.
